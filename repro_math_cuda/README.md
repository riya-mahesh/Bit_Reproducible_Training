# Reproducible math: exp, log, softmax

`repro_math.cuh` has correctly rounded `repro_expf` and `repro_logf`: the true value rounded once to float32. There is only one such answer, so the bits do not depend on the GPU, CUDA version, or CPU. They use only IEEE `+ - * / fma` (explicit `.rn` intrinsics on the GPU) and exact constants: no math library and no approximate hardware instructions. The same source compiles for the CPU.

- **Fast path:** FP32 float-float arithmetic, largest actual error 2^-44.8 (exp) and 2^-45.0 (log).
- **Rounding test:** if the error interval could contain a rounding midpoint, take the slow path.
- **Slow path:** double-double. Over all float32 inputs, true values stay at least 2^-51.7 (exp) and 2^-57 (log) from a midpoint, so it always decides. It runs for 625 of 2^32 inputs for exp and 2866 for log.

`repro_softmax.cu` computes softmax as `exp(x - max)` with `repro_expf`, an exact sum from `repro_sum`, and IEEE division (definition in `repro_softmax_math.cuh`). It runs as one fused kernel with one warp per row, or in separate stages when there are very few very long rows; both give the same bits. Backward is not implemented on its own, but cross-entropy has its gradient.

Cross-entropy is in the same files. The loss is `repro_logf(S) - (x[t] - max)` per row, then an exact mean over rows that are not ignored. The gradient is `seed * (e / S - one_hot) / count`, reusing `e` and `S` from the forward call's workspace.

**Apple M4 Pro CPU, all 2^32 inputs** (`results/mac/check_math.log`): 0 differences from the double-double reference for both functions, 0 of 19 hard cases wrong, and 0 of 1,072,568 wrong against a separate 300-bit `mpmath` recomputation of every slow-path input plus every 4096th input.

# Math functions: are they bit-identical across GPUs?

Elementwise functions (exp, log, tanh, sigmoid, erf, division, sqrt, …) have no summation order, so they are deterministic run to run on one setup. The open question is whether **different GPUs or CUDA versions** give the same bits. IEEE-754 requires correct rounding for `+ − × ÷ sqrt fma`, but **not** for transcendental functions such as `exp` or `tanh`, whose last bits depend on the implementation.

Float32 has only 2³² inputs, so this is tested **exhaustively**, not by sampling.

## What `exhaustive_math` measures

For each function, on all 4,294,967,296 float32 inputs:

- **hash of all outputs**: equal hashes on two GPUs mean identical results on every input;
- **per-block hashes** (4096 blocks of 2²⁰ inputs) to locate differences;
- **accuracy**: how many outputs differ from a double-precision reference rounded to float, and the largest difference in ulps.

| Name | What it is |
|---|---|
| `expf`, `logf`, `log1pf`, `expm1f`, `tanhf`, `erff` | CUDA math library (what PyTorch eager uses) |
| `sigmoid_torch` | PyTorch's formula `1 / (1 + expf(-x))` |
| `__expf` | fast-math intrinsic (approximate) |
| `exp_via_double` | RepDL's approach, `(float)exp((double)x)` |
| `sqrtf`, `recip_1/x`, `div_x/10` | IEEE operations — expected exact and identical everywhere |
| `rsqrtf` | approximate reciprocal square root |
| `mul_x*0.1f` | what `x/10` becomes if a library replaces division by multiplication |

Built with default `nvcc` flags (no `--use_fast_math`), like PyTorch.

Each function also gets a second hash, `<name>~nan`, with every NaN output replaced by one bit pattern. IEEE-754 leaves the bits of a NaN result implementation-defined (NVIDIA GPUs return `0x7fffffff`; x86/ARM CPUs return `0x7fc00000` or pass through the input's payload), so `<name>` can differ only because of NaN bits while `<name>~nan` shows that all numeric results agree.

`exhaustive_math_cpu.cpp` runs the same functions with the C library (glibc on Linux, Apple libm on macOS) on all 2³² inputs, multi-threaded, writing the same format so `compare_math.sh` can compare CPU against GPU. `__expf` is GPU-only; on the CPU `rsqrtf` is `1.0f/sqrtf(x)` (what PyTorch's CPU rsqrt does). PyTorch's own CPU kernels mostly use a different library again (SLEEF).

## Results so far

**GPUs, CUDA 12.4** (RTX 2080 Ti sm_75, TITAN V sm_70, RTX 4070 sm_89): all 14 functions bit-identical across all three architectures on all 2³² inputs, including approximate ones (`__expf`, `rsqrtf`).

| Function (CUDA 12.4) | ≠ double reference | max ulp |
|---|---|---|
| `expf` | 3.72% | 2 |
| `logf` | 1.69% | 1 |
| `tanhf` | 0.92% | 2 |
| `erff` | 8.64% | 1 |
| `sigmoid_torch` | 4.36% | 2,097,151 (returns 0 for x ≈ −104…−88.7, where `expf(−x)` overflows; true value is a tiny subnormal) |
| `rsqrtf` | 10.79% | 2 |
| `sqrtf`, `1/x`, `x/10` | 0 | 0 |
| `x*0.1f` vs `x/10` | 19.65% differ | 1 |

(`exp_via_double` shows 0 only because the reference is the same computation; it says nothing about its accuracy.)

**Apple M-series CPU (Apple libm) vs those GPUs:** IEEE operations (`sqrtf`, `1/x`, `x/10`, `x*0.1f`) give identical numbers on all 2³² inputs, differing only in NaN bit patterns. RepDL's `(float)exp((double)x)` is identical on all 2³² inputs, NaN bits included. `expf`, `logf`, `log1pf`, `expm1f`, `tanhf`, `erff`, and the sigmoid formula differ (Apple's library is more accurate: `expf` differs from the reference on 0.05% of inputs vs 3.7% for CUDA).

## Run

```bash
module load cuda-12.4                 # on CIMS
./run_math_test.sh                    # all GPUs on this machine; GPUS="0" for one
./run_math_cpu.sh                     # the CPU (glibc) version on this machine
./compare_math.sh results/cuda2/gpu0_*.txt results/cuda2/gpu1_*.txt     # two GPUs
./compare_math.sh results/cuda2/gpu0_*.txt results/cuda5/gpu0_*.txt     # two machines
build/exhaustive_math --dump tanhf 1016 > tanh_block1016.txt             # exact values of one block
```

Runs a few seconds to a minute per function (the double-precision reference is slow on GeForce GPUs).

Results depend on the CUDA version as well as the GPU; to test that, rerun after loading a different `module load cuda-…` and compare.
